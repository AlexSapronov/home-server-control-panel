# Мониторинг OpenWrt

Версия 0.2 читает состояние AdGuard Home, zapret и tg-ws-proxy через ограниченный SSH-ключ. Токен Proxmox, пароль панели и секрет Telegram-прокси не передаются на роутер и не выводятся в телеметрию.

## Что проверяется

| Показатель | Источник | Ограничение |
| --- | --- | --- |
| AdGuard / Telegram | `ubus service list`, только `running` | Процесс может работать с ошибками |
| zapret | procd; если записи нет — наличие `nfqws`, `nfqws2` или `tpws` в `/proc/*/comm` | Не проверяет правила и фактический обход DPI |
| DNS | UDP-запрос A `example.com` из контейнера на порт 53 роутера | Не измеряет блокировку рекламы и не гарантирует доступность всех DNS-имён |
| Порты AdGuard / Telegram | TCP-подключение из контейнера; по умолчанию 3001 / 1443 | Не проверяет авторизацию или работу протокола Telegram |
| WAN | `ubus network.interface.wan status` | Состояние интерфейса не является проверкой интернета |
| AmneziaWG | `awg show interfaces`, `latest-handshakes`, список интерфейсов netifd | Поднятый интерфейс не означает рабочий маршрут; handshake может отсутствовать |

Процессы не запрашиваются через `ps` с аргументами: команда Telegram-прокси может содержать секрет. Сборщик выбирает только разрешённые поля из ubus, не выдаёт командные строки или ключи VPN. Python и `ubus` нужны на OpenWrt; Python уже установлен, если на нём работает Python-прокси.

## Установка из контейнера панели

Сначала проверьте на OpenWrt fingerprint SSH-сервера:

```sh
dropbearkey -y -f /etc/dropbear/dropbear_ed25519_host_key
```

Вывод содержит публичный ключ и его fingerprint; приватный ключ не печатается. Сопоставьте fingerprint с запросом SSH при установке. Не удаляйте `known_hosts` при неожиданном несовпадении.

Затем в Proxmox: `pct enter 101` (замените ID, если контейнер другой). Внутри контейнера под root:

```sh
apt-get update
apt-get install -y openssh-client
cd /opt/home-server-control-panel
git pull --ff-only
python3 deploy/setup-openwrt.py 192.168.10.1
```

Адрес — LAN IP вашего OpenWrt. При первом подключении подтвердите проверенный fingerprint, затем введите пароль root роутера. Пароль читает сам SSH из терминала; он не сохраняется установщиком. Команда требует интерактивной консоли (`pct enter`, а не неинтерактивный `pct exec`).

Установщик:

1. Создаёт отдельный Ed25519-ключ от пользователя `nerv` в `/etc/nerv/ssh` (существующий ключ сохраняется).
2. Устанавливает `/usr/libexec/nerv-status.py` на роутере.
3. Добавляет ключ в `/etc/dropbear/authorized_keys` с фиксированной командой сбора состояния и запретом терминала, port forwarding, agent forwarding и X11. Остальные ключи сохраняются.
4. Копирует подтверждённую запись host key в отдельный `known_hosts` службы.
5. Проверяет SSH под пользователем `nerv`, обновляет `openwrt` в конфиге и перезапускает панель. До обновления конфигурации создаётся `config.json.before-openwrt`.

Используется root-аккаунт Dropbear, но этот конкретный ключ ограничен фиксированной командой. Ограничения опираются на корректную работу Dropbear. Сам сборщик не читает `SSH_ORIGINAL_COMMAND`, не вызывает shell и не выполняет операции изменения системы. Установочный вход root с паролем имеет обычные права администратора и используется только для размещения сборщика/ключа.

Повторный запуск сохраняет ключ, заменяет его запись ограниченной командой и не дублирует ссылку AdGuard. При ошибке установки можно исправить причину и запустить повторно. Не используйте ключ панели для других задач.

## Работа и диагностика

SSH-данные и проверки сети кэшируются на 15 секунд, общих для вкладок. При потере SSH прежние значения служб остаются с подписью и временем последнего успешного сбора; свежие проверки DNS/портов показываются отдельно. Отказ OpenWrt не блокирует метрики Proxmox.

В деморежиме никакие подключения к роутеру не выполняются. В LIVE без блока `openwrt.enabled=true` отображается «не подключён»; устанавливать интеграцию для работы Proxmox не обязательно.

При ошибке:

```sh
systemctl status nerv-panel --no-pager
journalctl -u nerv-panel -n 40 --no-pager
```

SSH stderr не возвращается браузеру: там может оказаться чувствительная информация из окружения/сервера. Проверяйте существование ключей, права доступа пользователя `nerv`, запись host key и наличие Python/ubus на OpenWrt. Не отключайте `StrictHostKeyChecking`.

Чтобы отключить мониторинг, задайте `openwrt.enabled=false` в `/etc/nerv/config.json` и перезапустите службу. Это не останавливает службы роутера. Для полного удаления удалите только строку ключа `nerv-panel-monitor` из `/etc/dropbear/authorized_keys` и `/usr/libexec/nerv-status.py`.

## Управление сайтами AWG

Установите мониторинг, затем из каталога панели под root в LXC выполните:

```sh
python3 deploy/setup-awg.py
```

Установщик использует root SSH для однократной установки `/usr/libexec/nerv-routing.py`, создаёт отдельную пару ключей `openwrt_awg_ed25519`, проверяет ограниченное подключение от пользователя `nerv` и включает `openwrt.routing_enabled` в конфигурации панели. Существующий ключ мониторинга сохраняет доступ только к телеметрии. Ключ управления допускает только команду `nerv-awg` с JSON через stdin; shell и перенаправление портов запрещены. Отключение функции: `routing_enabled=false` и перезапуск панели; это сохраняет уже настроенные маршруты.

На OpenWrt нужны Python 3, PBR, `awg0`, nftables и режим DNS `dnsmasq.nftset`. Клиенты должны использовать DNS роутера: отдельный DoH в приложении обходит наполнение доменных наборов. Для IPv6 маршрутизация PBR должна быть настроена отдельно; эта интеграция проверена с IPv4 AWG.

«Сайты через AWG» показывает текущие общие правила `awg0` с доменами и без дополнительных ограничений. «Выкл» сохраняет правило, переводя его в `enabled=0`; «Вкл» возвращает `enabled=1`. Домены видны и редактируются в раскрывающемся блоке каждой записи. Для YouTube, X и ChatGPT выберите готовый набор, чтобы увидеть связанные домены до сохранения. Свой сайт можно задать по имени или ссылке и дополнить доменами API/CDN. Поддомены включены автоматически, IP определяет DNS. Прямые исключения WAN сохраняют приоритет; существующие правила отдельных устройств не доступны для редактирования.

API `/api/router/awg-sites` работает только в LIVE с `NERV_PASSWORD`. GET читает правила и готовые наборы. POST принимает `action=add` с `domain` и необязательным массивом `extra_domains`, `action=set_enabled` с `id` и boolean `enabled` или `action=update_domains` с `id` и массивом `domains`. Каждый POST требует актуальную `revision`, JSON и заголовок `X-NERV-Action: awg-routing`. Одновременные изменения сериализуются на роутере, устаревшие запросы отклоняются. Несохранённые изменения PBR в LuCI также блокируют запись.

Перед записью сохраняются последние 10 копий `/etc/config/pbr` в `/etc/nerv-routing-backups/`. После применения перезапускается только PBR, проверяется создание nft-наборов и восстанавливаются накопленные IP действующих правил. Домены нового сайта предварительно запрашиваются через локальный dnsmasq с учётом его порта. При ошибке применения восстанавливается предыдущая конфигурация. Текущие соединения и клиентский DNS-кэш могут продолжать использовать прежний маршрут до переподключения/истечения TTL.

Если SSH-ответ потерян во время применения, обновите список перед повтором. Ошибка связи не означает, что операция не выполнилась. Исходный список сайтов хранится на роутере и переживает перезапуск панели.

## Диагностика сайта

После обновления кода панели повторно запустите `deploy/setup-awg.py`, чтобы установить вместе с ограниченным SSH-обработчиком модуль `/usr/libexec/nerv_diagnostics.py`. Новая пара SSH-ключей не создаётся, если ключ управления AWG уже есть. Установщик перезапускает только панель в LXC; сетевые службы OpenWrt не перезапускает.

POST `/api/router/diagnose` принимает JSON `{"target":"https://example.com/resource"}` и заголовок `X-NERV-Action: site-diagnostics`. Нужны LIVE, пароль панели, включённая интеграция AWG и запрос из той же страницы. Переданные клиентом другие действия игнорируются: сервер всегда посылает фиксированный `action=diagnose` через ограниченный ключ.

В результате есть отдельное действие «Включить через AWG». Оно использует существующий API управления AWG: сначала GET актуального списка/revision, затем `add` проверенного домена либо `set_enabled` сохранённого правила, покрывающего этот домен. URL в поле можно изменить после проверки — действие всё равно относится к последнему завершённому результату. После успешного применения обновляются список и диагностика исходной ссылки. Если правило уже включено, выполняется только повторная проверка; если есть общее прямое WAN-исключение, быстрое включение недоступно. Сам туннель не перезапускается; явное изменение правила использует существующее применение PBR с резервной копией и откатом. Ошибка записи не выдаётся за успех, повторная попытка снова читает список.

Проверка использует DNS на `127.0.0.1:53`, читает UCI/PBR и nftables и вычисляет первое совпавшее общее IPv4-правило в `pbr_prerouting`. Учитывается реальный IP-набор, а не только предполагаемое совпадение домена. Для отсутствующего набора, общих CDN-адресов и отключённых правил результат показывается отдельно. Правила конкретных устройств и другие сложные условия не моделируются.

Путь проверяется командой `ip route get` с найденной меткой, затем выполняются ограниченные GET через существующие WAN/AWG-интерфейсы. Службы не запускаются и не перезапускаются, UCI/nftables/ip rules не записываются. Обычный DNS-запрос может штатно наполнить DNS-кэш и связанные PBR-наборы.

Ограничения HTTP: публичные домены, порты 80/443, до двух IPv4, два параллельных запроса, диапазон 0–65535, предел ответа 1 МиБ, тайм-аут соединения 3 с и запроса 8 с. При игнорировании Range и большом файле возвращается результат «превышает лимит». HTTPS-сертификаты проверяются. IP фиксируется через `--resolve`, прокси и curl-конфиги отключены, перенаправления не выполняются. Локальные/специальные DNS-адреса и URL с учётными данными отклоняются. В ответ не попадают тело страницы, cookies, заголовки, stderr и параметры ссылки перенаправления.

Для повторяемой проверки использован `https://rutracker.org/`: DNS разрешается, текущий общий маршрут WAN, через WAN ошибка TLS, через AWG HTTP 301. Конфигурации network/firewall/pbr/dhcp совпали по SHA256 до и после проверки. Результат может измениться со временем и не является постоянной гарантией доступности сайта.
