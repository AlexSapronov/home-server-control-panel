# Стратегии DPI в NERV

Раздел управляет профилями zapret для домашнего OpenWrt. NERV хранит очередь, отчёты и версии в SQLite. Отдельная VM выполняет подбор и проверки. OpenWrt забирает подтверждённые версии и ждёт команды на активацию. Зонд в домашней LAN проверяет результат после переключения.

## Топология

| Узел | Подключение по исходной схеме | Что подтвердить на месте |
| --- | --- | --- |
| Proxmox `homeserver` | Управление из LAN, наблюдавшийся адрес `192.168.10.2` | Актуальный адрес и состояние мостов |
| OpenWrt VM 100 | `net0` → `vmbr-lab` → `br-lan`, `192.168.10.1/24`. `net1` → `vmbr0` → `eth1`, WAN через DHCP | Имена устройств, WAN-маршрут и физический порт WAN. В исходном снимке `vmbr0` использовал `nic4` |
| NERV CT 101 | `eth0` → `vmbr-lab`, адрес выдаётся по DHCP. Наблюдался `192.168.10.119` | Стабильное имя панели с валидным сертификатом, HTTP-ответ через HTTPS-прокси, доступ к API по назначению |
| Домашняя LAN | `vmbr-lab`, `192.168.10.0/24`, в исходном снимке `nic1`, `nic2`, `nic3` | Маршрут зонда и доступность DNS OpenWrt |
| Стенд | Новый мост, например `vmbr-dpi`, без IP Proxmox и физических портов. Дополнительные NIC OpenWrt и воркера на этом мосту. Пример адресов `192.168.91.1/29` и `192.168.91.2/29` | Нет пересечения подсетей. Тестовый маршрут через WAN VM 100, отдельная сеть управления воркером |

До подключения снимите `qm config 100`, `pct config 101`, `ip -br addr`, `ip -4 route` и конфигурацию мостов на Proxmox. На OpenWrt сверяйте `ubus call network.interface.wan status`, `ip -4 route`, `nft list ruleset` и `/opt/zapret/config`. Сохраните исходные конфиг zapret и hostlists с правами и владельцами. Проверьте наличие резервной копии VM 100. Сведения в таблице взяты из исходного ТЗ, фактические значения на живом хосте требуют сверки.

У воркера два интерфейса. Сеть управления пропускает воркер к HTTPS API NERV. Второй интерфейс поднимается внутри отдельного Linux network namespace, использует статический адрес и выходит через единственную WAN-аренду OpenWrt. Стенд не подключается к `vmbr0`.

### Изоляция тестового маршрута

1. Создайте отдельную зону OpenWrt для тестовой подсети. Запретите вход к самому роутеру и маршрутизацию в LAN, VPN и другие зоны управления. Разрешите из неё IPv4 TCP 80/443 к публичным адресам в WAN и TCP/UDP 53 к выбранному публичному DNS. Заблокируйте локальные, зарезервированные и служебные сети и доступ к адресам управления, включая WAN-адрес роутера, если с него доступно управление или настроен DNAT. Учитывайте IPv6 в политике зоны и отключите его на этом маршруте.
2. Проверьте, что тестовый трафик маршрутизируется через WAN провайдера при наличии VPN и policy-based routing. Проверьте, что OpenWrt применяет NAT для тестовой подсети.
3. Исключите тестовые соединения из **обоих направлений** NFQUEUE рабочего zapret. В zapret v72.13 `FW_EXTRA_POST` используется при создании исходящих и ответных правил. Для правил IPv4 может подойти условие `ct original ip saddr != 192.168.91.0/29` в существующем `FW_EXTRA_POST`, с подстановкой фактической подсети. Сохраните остальные условия. Сверьте с установленной версией и структурой правил. После перезапуска проверьте, что условие попало в обе цепочки и что тестовое соединение не увеличивает счётчики NFQUEUE, а проход из LAN увеличивает. Краткая трассировка пакетов по выделенному соединению позволяет отличить его от фонового трафика.
4. Из namespace подтвердите доступность контрольного публичного сайта и проверьте отказ соединений к адресам LAN, Proxmox и панели. Проверьте, что выключение воркера не меняет доступность сервисов из LAN.

## Установка

На всех узлах нужны синхронизированные часы и доверие к TLS-сертификату NERV. Для каждого из трёх клиентов сгенерируйте свой случайный токен, например `openssl rand -hex 32`. Клиенты считывают токен из файла, указанного в `token_file`. Для NERV используйте `NERV_DPI_WORKER_TOKEN`, `NERV_DPI_ROUTER_TOKEN` и `NERV_DPI_LAN_TOKEN` в `/etc/nerv/panel.env`. Пароль `NERV_PASSWORD` обязателен. HTTPS-прокси должен передавать `Authorization` и `X-NERV-Request` и держать интерфейс и API в доверенной сети.

### NERV и LAN-зонд

1. Обновите checkout панели и unit `nerv-panel.service`. Unit создаёт `/var/lib/nerv-panel` для SQLite. Скопируйте настройки `dpi` из [config.example.json](../config.example.json), подберите контрольный URL и доступное из вашей сети публичное видео YouTube, заменив `_YOUR_VIDEO` на его ID. Для Discord укажите стабильный публичный ресурс. При необходимости задайте `tls` как `1.2` или `1.3` и `min_bytes` по фактическому ответу. По умолчанию ревизия пропускает окно 02:45–04:00 МСК, проверка идёт каждые 6 часов, ревизия раз в неделю.
2. Разместите [lan.example.json](../deploy/dpi/lan.example.json) как `/etc/nerv-dpi/lan.json` в LAN CT или на другой LAN-машине. Укажите IP OpenWrt в `dns_host`. Нужны Python 3.11+, curl и актуальный yt-dlp с зависимостями, которые требует выбранный видеоформат. Установите [nerv-dpi-lan.service](../deploy/dpi/nerv-dpi-lan.service), дайте пользователю `nerv` чтение только своего токена. Зонд не запускается в тестовом namespace. Его соединения к контрольным URL должны идти через VM 100.
3. Включите `dpi.enabled=true`, выполните `systemctl daemon-reload` и перезапустите `nerv-panel`. Запустите `nerv-dpi-lan`. Если зонд и панель на разных узлах, обновите checkout и настройки на каждом из них.

### Тестовая VM

На Debian установите Python 3.11+, `iproute2`, `nftables`, `procps`, curl, dnsutils, CA и актуальный yt-dlp с его зависимостями. Подключите только выделенный NIC к тестовому мосту и исключите этот NIC из DHCP, сетевых профилей и перенаправлений внутри VM. Ядру нужны `nf_conntrack`, `nfnetlink_queue` и `nft_queue`. Если не загружаются автоматически, добавьте их в `/etc/modules-load.d/`. В /opt/zapret разверните тот же релиз nfqws и соответствующий ему blockcheck, что использует OpenWrt. Для v72.13 используйте выпуск [zapret v72.13](https://github.com/bol-van/zapret/releases/tag/v72.13). Нужны бинарники nfqws и mdig, каталог upstream и запускаемый `blockcheck.sh`. Запустите `nfqws --version` на обоих узлах и сверьте строку версии и ревизии.

Скопируйте checkout в `/opt/home-server-control-panel`. Заполните [worker.example.json](../deploy/dpi/worker.example.json) и установите файл как `/etc/nerv-dpi/worker.json`. В `test_deny` укажите дополнительные сети и адреса, к которым стенд не должен обращаться. Установите и запустите [nerv-dpi-worker.service](../deploy/dpi/nerv-dpi-worker.service). Сервис создаёт namespace, переносит выделенный NIC и ограничивает исходящие соединения. После остановки сервиса процессы завершаются, временные правила пропадают вместе с namespace, а NIC возвращается в основное пространство имён VM.

### OpenWrt

Python 3 и системный CA должны быть доступны. Разместите `dpi_router.py`, `dpi_agent.py` и `dpi_policy.py` в `/usr/lib/nerv-dpi/`. Скопируйте [router.example.json](../deploy/dpi/router.example.json) в `/etc/nerv-dpi/router.json`, задайте имя панели, сертификат и сопоставление фактических hostlist. Каталог состояния и токен должны быть доступны только root. Перед запуском проверьте импорт без записи в рабочий конфиг:

```sh
python3 /usr/lib/nerv-dpi/dpi_router.py /etc/nerv-dpi/router.json --inspect
```

В импорте поддерживается статический блок nfqws TCP/443 с отдельным текстовым hostlist на профиль, `MODE_FILTER=none`, IPv4 и известными параметрами v72.13. IPv4 должен ограничиваться `--filter-l3=ipv4` или общим `DISABLE_IPV6=1`. Конфигурации с другими профилями, нестандартными параметрами или динамическими hostlists требуют предварительной адаптации. Убедитесь, что выбранные правила, лимиты пакетов и фактические цепочки nftables соответствуют снимку. `tg-ws-proxy` и AdGuard в управление профилями не входят.

Установите [nerv-dpi-openwrt](../deploy/dpi/nerv-dpi-openwrt) как `/etc/init.d/nerv-dpi` с правом исполнения. Запустите `/etc/init.d/nerv-dpi start`, проверьте отображение снимка в NERV и включите `/etc/init.d/nerv-dpi enable`.

## Подбор, проверка и восстановление

- NERV принимает публичные HTTP(S)-адреса со стандартным портом. Контрольная проверка использует путь, параметры запроса и фрагмент удаляются. В адресах с логином или паролем запрос отклоняется. На каждом редиректе зонд повторно проверяет адрес и закрепляет конкретный публичный IPv4 для соединения.
- Плановая ревизия повторяет подбор для рабочих профилей. Кандидат проходит две серии по три попытки, подтверждение по умолчанию действует 48 часов. YouTube требует загрузки страницы и первого 1 МиБ видеоданных по диапазону HTTP. Сайт Discord проверяется по полному телу ответа и установленному минимуму. Голос Discord, IPv6 и QUIC не проверяются. В журнале видны время серий, IP, байты и причины отказов.
- Доставленный кандидат ждёт кнопки «Применить на OpenWrt». Автопереключение включается в карточке профиля и срабатывает после подтверждённых последовательных сбоев, при наличии свежей версии и LAN-зонда. Плановая ревизия сама активный профиль не меняет.
- При активации роутер повторно проверяет версию, контрольную сумму, свежесть и отпечаток конфигурации. Снимок и журнал записываются перед изменением файлов. Профиль восстанавливается при отрицательном результате LAN-зонда, истечении локального срока либо перезапуске агента до подтверждения. Ручной откат к предыдущему профилю доступен при совпадении текущего отпечатка с отпечатком после применения.
- Для локального восстановления остановите `/etc/init.d/nerv-dpi`, затем выполните следующую команду. Она обрабатывает незавершённую операцию, восстанавливает сохранённые файлы и поднимает zapret. Если операция уже завершена и агент недоступен, используйте исходную копию конфига и hostlists.

```sh
/etc/init.d/nerv-dpi stop
python3 /usr/lib/nerv-dpi/dpi_router.py /etc/nerv-dpi/router.json --recover
/etc/init.d/zapret status
```

## Приёмка

| Шаг | Проверка |
| --- | --- |
| Ревизия | Запустите ручную ревизию и проверьте расписание. Рабочий профиль YouTube тоже должен пройти новый поиск |
| Валидация | Сравните полные загрузки без обработки, с активным профилем и с кандидатом. Оборванный ответ после HTTP 200 не должен пройти |
| Доставка | Проверьте статус доставки и свежесть. Убедитесь, что отпечаток рабочего конфига не изменился |
| Активация | Примените доставленный профиль из NERV при доступном LAN-зонде. Проверьте запущенную службу, целевой и соседний профиль, DNS и контрольный сайт |
| Откат | На тестовом роутере прервите связь с NERV во время проверки или подайте отрицательный результат LAN-зонда. Сверьте восстановленный конфиг и hostlist с исходными копиями |
| Изоляция | Проверьте, что смена конфига вручную делает пакет устаревшим, выключение воркера завершает задачу по таймауту, а редирект в LAN блокируется до соединения |

Локальные тесты проходят с файловым журналом роутера и эмуляцией службы zapret, LAN-зонда и доступа к NERV. Живые проверки включают фактический импорт, отсутствие попадания тестового потока в рабочую NFQUEUE, подбор через провайдера, DNS и передачу видеоданных, активацию и восстановление на OpenWrt. Их нужно провести на доступной инфраструктуре.
